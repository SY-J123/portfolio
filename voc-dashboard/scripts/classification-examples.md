# 분류 경계 사례집

## 분류 개선 워크플로

1. **초기 분류** — `classification.md` 규칙만으로 LLM이 전체를 분류해 기준선을 확보한다.
2. **소규모 샘플 검토·정정** — 사람이 분류 결과를 소규모 샘플로 훑으며 잘못 붙은 레이블을 정정한다. 정정 케이스는 이 파일에 (원문 → 정답 → 근거)로 기록된다.
3. **정정 기록을 참고한 재분류** — `classify-all.ts`가 다음 분류 호출 시 `classification.md`(규칙)와 이 파일(사람 정정 기록)을 함께 프롬프트에 주입한다. LLM은 사람이 정정한 케이스를 few-shot 예시로 참고해 동일 패턴의 리뷰에 일관되게 적용한다.
4. **반복** — 정정 누적이 쌓이면서 공통 패턴이 보이면 `classification.md`의 규칙으로 승격한다.

대규모 골든셋을 한 번에 만들지 않고, 사람이 실제 걸리는 케이스를 정정하면서 그 기록을 분류 자료로 쌓는 접근.

## 경계 사례 (규칙으로 충분히 기술되지 않는 엣지 케이스)

### #1 빈도·분량 불만 (광고·팝업·알림)

**원문**: "페이스페이 광고좀 그만 띄우세요 너무 편리해서 다른 거 다 좋은데 페이스페이 쓰라고 하도 강요하고 보여줘서 어플 삭제하고 싶어요. 페이스페이 안 쓴다고요"

- **types**: `["user_experience"]`
- **sentiment**: `negative`
- **근거**: 기능명(페이스페이)이 들어가지만 "광고 그만 띄워라"는 노출 빈도·강요 불만. 기능 추가·변경 요구 아님. §1.3 빈도·분량 불만 규칙.

---

**원문**: "하단 쇼핑탭 광고 팝업좀 그만 띄워주세요 너무 불편해요 ui가 편해서 쓰고있었는데 진짜 업데이트 할때마다 이런식으로 선넘는 업데이트만 하니 너무 실망스럽네요"

- **types**: `["user_experience"]`
- **sentiment**: `negative`
- **근거**: 팝업 빈도 축소 요구 + UI 변경 불만. 둘 다 UX 영역.

---

**원문**: "이젠 쇼핑몰까지 할려고?? 쇼핑몰 광고도 드럽게 하네 진짜 쇼핑몰 클릭유도 팝업 좀 없애라 꼴랑 천원할인권에 타업체보다 훨씬 비싸게 팔면서 광고 진짜 오지게 하네 적당히 해라 좀"

- **types**: `["user_experience"]`
- **sentiment**: `negative`
- **근거**: "쇼핑몰 클릭유도 팝업 좀 없애라" → 팝업 축소 요구가 핵심. 중간에 상품가·서비스 모델 비판("타업체보다 비싸게")이 섞여있지만 이는 구체 기능 요구가 아니라 부수적 감정 표출. 전체적으로 광고·팝업 빈도 불만 프레임. → UX.

---

**원문**: "페이스 페이 광고 좀 작작해라!"

- **types**: `["user_experience"]`
- **sentiment**: `negative`
- **근거**: 한 줄 명령조이지만 본질은 "광고 빈도 줄여라" 요구. 짧은 길이·감탄형에도 rating(하소연)이 아닌 UX로 가는 이유: 구체 대상("페이스 페이 광고")과 요구 방향("작작 = 줄여라")이 명확함. 기능 추가·변경 요구도 아니고 오작동도 아님 → UX.

### #2 기존 오류 재발·미해결 + 환경 호환성

**원문**: "9 오류 아직 못고친건가 웹에서 아이패드로 증권하기 불편하네요"

- **types**: `["bug_report"]`
- **sentiment**: `negative`
- **근거**: "아직 못고친건가" → 기존 오류 미해결 언급 (버그 재발 확인). "웹에서 아이패드로 증권하기 불편" → 특정 환경(아이패드 웹) 한정 동작 문제로 호환성 버그. "불편"이라는 감정 어휘로 끝나도 실제로는 기능이 제대로 안 되는 상황.

---

### #3 하소연형 단문 (오작동 시그널이지만 구체성 없음)

**원문**: "주식이 안되요~~~ 이게 무슨일인죠????"

- **types**: `["rating"]`
- **sentiment**: `negative`
- **근거**: "안 되요" 오작동 시그널은 있지만 구체 기능(주식은 광범위)·상황·재현 맥락 전무. 감탄사·물음표만 있음. 실무 분석 가치 낮음 → rating 버킷.

---

**원문**: "렉이 너무심하고 앱내 기능이 실행이안됨"

- **types**: `["rating"]`
- **sentiment**: `negative`
- **근거**: "렉"·"실행 안 됨" 오작동 시그널 2개 있지만 "앱내 기능"이 어떤 기능인지·어느 시점·어느 조작에서인지 전무. 재현 맥락·특정성 부족. 문장 구조는 갖췄지만 내용이 없어 하소연형. → rating.

---

**원문**: "코스뱅크를 쓸수 없다면서 개인정보릉 확인하래요ㅠㅠㅠㅠ 토그뱅크ㅜㅠㅠㅠㅠ"

- **types**: `["rating"]`
- **sentiment**: `negative`
- **근거**: 오타(코스뱅크→토스뱅크)·반복되는 이모티콘·끊어진 문장 구조로 인해 무엇이 잘못됐는지 맥락 파악 불가. "쓸 수 없다"는 오작동 시그널 비슷하지만 구체 상황·조작·재현 조건 전무. 감정 표현 위주. → rating.

**판정 팁**: 오작동 시그널 개수가 아니라 "어느 기능·화면·조작에서"의 **특정성**이 핵심. 기능이 광범위하거나("앱내 기능", "주식", "결제") 오타·이모티콘에 가려 맥락이 끊긴 경우도 하소연형으로 본다.

---

### #4 기존 기능 정책·조건 변경에 대한 불만

**원문**: "아 뭐여. 고양이미션하려고 매일 토스로 결제해서 사료랑 장난감 모아뒀더니, 이거 시간제한 생겼네요? 그동안 모아둔거 다 날아감. 별거아닌데 열받네"

- **types**: `["user_experience"]`
- **sentiment**: `negative`
- **근거**: "시간제한 생겼네요" → 기존 기능 정책 변경. "모아둔거 다 날아감" → 결과로 인한 경험 저하. 명시적 변경 요구 없이 불만만 토로. §1.3 정책·조건 변경 불만 규칙.

---

### #5 기존 배치 복원 요구 (부수적 성능 언급 포함)

**원문**: "고양이 키우기 원 위치로 되돌려 놔요 쇼핑에서 시간 잡아 먹고 버벅됨 본 위치로"

- **types**: `["user_experience"]`
- **sentiment**: `negative`
- **근거**: "원 위치로 되돌려 놔요" → 옛날 배치 복원 요구. §2.3 (2)번 규칙 ("있는 요소를 옛날 정책으로 되돌리는" → UX). "버벅됨" 성능 언급이 있지만 부수적이고 구체적 서술 없음 → 독립 bug_report 추가하지 않음.

**주의**: "버벅됨" 같은 단발성 성능 불만이 UX 복원 요구와 함께 나올 때, 메인 불만이 UI/정책 복원이면 UX 단독. 만약 성능 문제가 리뷰의 메인 주제고 구체 상황("결제 화면 열 때마다 3초 멈춰요")이 있으면 bug_report 동반 분류.

---

### #6 광범위 UX·리워드 설계 불만 중 부수적 "먹통" 언급

**원문**: "무슨 만보기 복권하나 받고 긁기 힘들다 꼴랑 10~20원 주면서 영상봐야 복권긁기되고 영상 누루면 5~6번 해도 계속 먹통 수준 아 욕이 절로 나옴 왜만든거임?"

- **types**: `["user_experience"]`
- **sentiment**: `negative`
- **근거**: 리뷰의 **주제**는 "만보기 복권" 기능의 설계·리워드 구조 불만("긁기 힘들다", "꼴랑 10~20원", "왜 만든거임"). "먹통" 언급이 있지만 그것이 독립적인 기술 오류 신고가 아니라 "영상 여러 번 눌러도 보상을 얻기 어렵다"는 설계 불만을 증폭시키는 서술 장치. 기본은 UX 프레임으로 분류.
- **참고**: 만약 "영상 재생 중 앱이 튕겨요" 같이 **기술 오작동**이 명확히 서술돼 있으면 `bug_report`도 병기. 이 예시는 "먹통 수준"이라는 모호한 은유 표현이라 독립 버그 분류 안 함.

**판정 팁**: "먹통"·"안 됨" 단어가 있다고 자동으로 bug_report를 찍지 않는다. **주제가 설계·리워드·정책에 대한 불만**이고 오작동 언급이 부수·은유적이면 UX 단독.

---

### #7 원치 않는 알림이 오는데 끌 방법이 없음 (opt-out 결함)

**원문**: "쇼핑을 한적도 없고 쿠폰을 달랜적도 없는데 강제적으로 알람띄우고 당장 센터는 내가 끄는 방법이 없대 니들이 꺼줘야 된대 것도 또 쇼핑인지 뭔지로 이동해서 통화하고 입력한정보 또 나불대야 하고 그걸또 기다리래. 정도껏해 포인트 몇십원땜에 이거쓰냐? 기본만하라고"

- **types**: `["bug_report"]`
- **sentiment**: `negative`
- **근거**: 사용자가 동의/행동한 적 없는 알림이 발송되고, **설정에서 끌 방법이 없다는 구조적 결함** (고객센터도 "자체 해제 불가"로 확인). 이는 기능 결함 — opt-out 설정이 없거나 작동하지 않는 상황이므로 bug_report. "알림 그만 와요" 같은 단순 빈도 불만과는 성격이 다름.

**#1과의 경계**:
- #1 "푸시 알림 너무 많이 와요" → **빈도 불만**, 설정 가능 여부 언급 없음 → `user_experience`
- #7 "알림 오는데 끌 수가 없대요 / 끄는 방법이 없다" → **opt-out 기능 부재·오작동** → `bug_report`
- 핵심 차이: 사용자가 스스로 제어할 수단이 있느냐. 제어 수단 부재가 명시되면 버그.

## 프롬프트 주입 규칙 (classify-all.ts용)

- 위 사례들은 각각 **판별이 까다로운 경계 케이스**다. 평범한 리뷰는 `classification.md`의 규칙으로 충분히 분류 가능.
- LLM에게 few-shot 예시로 제공할 때, 각 사례의 **원문·types·근거**만 함께 전달해 "왜 이렇게 분류했는지"를 학습하도록 유도한다.
