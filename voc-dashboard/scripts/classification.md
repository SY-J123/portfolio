# VOC 리뷰 분류 가이드

이 문서는 토스 앱 리뷰를 Maalej et al. (2016)의 4분류 체계에 따라 다중 라벨 분류할 때 사용하는 단일 기준이며, 각 리뷰에 감정 라벨(긍정/부정/중립)을 함께 부여하는 규칙도 포함한다. LLM 프롬프트는 이 문서를 참조해 구성되며, 분류 규칙이 변경될 경우 본 문서만 수정하면 전체 재분류가 동일한 기준으로 수행된다. 범주별 30건씩 무작위 추출해 육안으로 검토하면서 오판정·경계 사례에 맞춰 규칙을 반복 조정한 산출물이다.

---

## 1. 분류 체계 (4유형)

한 리뷰에 최대 2~3개까지의 라벨을 허용한다. 해당되는 유형이 없으면 빈 배열(`[]`)로 반환한다.

**버그 우선 원칙**: 버그 리포트는 의사결정 가중치가 가장 높은 라벨이므로, 두 유형 사이에서 애매한 경우 `bug_report`를 우선 포함한다. 놓치지 않는 쪽을 택해 보수적으로 라벨링한다.

### 1.1 버그 리포트 (`bug_report`)

**정의**: 앱의 오류·비정상 동작을 신고하는 리뷰.

**판별 신호**:
- 튕김·먹통·꺼짐·오류·에러 등 명시적 오류 언급
- 특정 기능이 작동하지 않는다는 서술 ("로그인 안 돼요", "송금이 실패해요")
- 예상 동작과 실제 동작의 불일치 ("버튼을 눌러도 반응이 없어요")
- **"아직 못 고쳤냐" 같은 기존 오류 재발·미해결 언급** ("9 오류 아직 못고친건가", "OO 버그 업데이트해도 그대로네요")
- **특정 플랫폼·환경에서만 동작이 이상한 호환성 문제** ("웹에서 아이패드로 증권하기 불편하네요", "태블릿에서 화면이 깨져요") — "불편하네요" 같은 감정 어휘로 끝나도 "특정 환경에서 기능이 제대로 안 됨"을 의미하면 버그
- 업데이트 이후 발생한 이상 동작 ("업뎃 후 자꾸 튕깁니다")

**예시**:
- "로그인하면 계속 튕겨요"
- "송금하려는데 오류 메시지가 뜨면서 안 됩니다"
- "푸시 알림이 며칠째 안 와요"
- "9 오류 아직 못고친건가요?" (기존 오류 미해결 확인 — 언급 자체가 버그 신호)
- "웹에서 아이패드로 증권하기 불편하네요" (특정 환경 동작 불능 — "불편"이지만 호환성 문제)

**판정 팁**: "오류", "안 됨", "실패", "에러", "못 고쳤다" 같은 오작동 시그널이 하나라도 명시적으로 들어 있으면 감정 어휘·UX 불만이 섞여 있어도 **버그 우선 원칙**에 따라 `bug_report`를 포함한다.

**반례 — 버그가 아닌 것 (`rating` 처리)**:
- 오작동 시그널이 있어도 **구체 기능·상황·재현 맥락이 전혀 없고 감탄사·물음표·느낌표 위주의 단문**은 실무 분석 가치가 거의 없어 버그 리포트로 치지 않는다. 이런 하소연형 리뷰는 `rating`으로 분류한다.
  - "주식이 안되요~~~ 이게 무슨일인죠????" → `rating` (기능은 '주식'으로 광범위, 구체 서술 없음, 감탄사만 있음)
  - "앱이 이상해요!!!!!" → `rating`
  - "왜 안되죠 진짜" → `rating`
- 기준: 어떤 기능·화면·조작에서 무슨 일이 일어났는지 최소한의 서술이 있으면 `bug_report`, 단순 "안 돼요" 감탄만 있으면 `rating`.

### 1.2 기능 요청 (`feature_request`)

**정의**: **없는 기능의 추가**나 **기존 기능의 동작 변경**을 제안하는 리뷰. 요구의 핵심이 "새 기능 만들기 / 기존 기능 바꾸기"여야 한다.

**판별 신호**:
- "~해주세요", "~하면 좋겠어요", "~가 있으면" 등 요청·제안 어투
- 현재 없는 기능의 존재를 가정하는 서술 ("왜 X 기능은 없나요?")
- 특정 기능의 부재에 대한 아쉬움·불만 표현 ("다크모드 없어서 아쉽네요")
- 타 서비스와 비교한 개선 요구 ("카카오페이처럼 ~를 추가해주세요")

**예시**:
- "내역에 월별 필터 기능 추가해주세요"
- "다크 모드가 있으면 좋겠습니다"
- "결제 카드 우선순위 변경 기능이 필요합니다"
- "다크모드 없어서 아쉽네요" (특정 기능 부재 언급 → 기능 갭 신호)

**주의 (UX와 혼동 금지)**: "광고 그만 띄우세요", "팝업 없애주세요" 같은 **빈도·분량·노출 줄이기** 요구는 기능 추가·변경이 아니라 사용 경험 불만이다 → `user_experience`.

---

### 1.3 사용자 경험 (`user_experience`)

**정의**: 사용 중 경험한 감정·불편·만족을 서술하는 리뷰. 구체적 오류나 기능 요청이 아닌 사용 경험에 대한 인상 서술.

**판별 신호**:
- 불편함·편리함·혼란스러움·헷갈림 등 감정·평가 서술
- 특정 동작·흐름에 대한 경험 묘사 ("송금 UI가 헷갈려요", "결제가 빨라서 좋아요")
- UI·UX의 이해도·직관성·만족도에 대한 평
- "처음 썼는데~" 같은 경험 자체에 대한 서술
- **광고·팝업·알림의 빈도·분량·노출 과다**에 대한 불만 (기능명이 섞여도 빈도 불만이면 여기)
- **기존 기능의 정책·조건 변경**(시간제한 신설, 보상 축소·소실, 혜택 감소 등)으로 경험이 나빠졌다는 하소연. 명시적 변경 요구 없이 불만만 드러내면 UX.

**예시**:
- "송금 흐름이 헷갈려서 처음엔 어려웠어요"
- "UI가 깔끔하고 직관적이라 편합니다"
- "메뉴 구조가 너무 복잡해서 원하는 기능을 찾기 어렵습니다"
- "페이스페이 광고 좀 그만 띄우세요" (특정 기능 홍보 노출 과다 불만)
- "하단 쇼핑탭 광고 팝업 그만 띄워주세요" (팝업 빈도 불만)
- "광고 없애주세요" (기능 추가·변경이 아닌 빈도 축소 요구)
- "푸시 알림 너무 많이 와요"
- "고양이미션 시간제한 생겼네요? 모아둔거 다 날아감" (정책 변경에 대한 불만, 구체 요구 없음)
- "업데이트 이후 혜택 줄어들어서 아쉬워요" (혜택 축소 불만, 경험 저하)

---

### 1.4 평가 (`rating`)

**정의**: 오류·요청·경험 언급 없이 단순 칭찬·비난·감탄만 담긴 리뷰.

**역할**: 이 카테고리는 실질 분석 대상이 아니며, 전처리에서 걸러지지 못한 **정보 가치가 낮은 리뷰를 모아두는 버킷** 역할이다. 주요 인사이트(버그 패턴·기능 요청·UX 이슈)는 나머지 3개 카테고리에서 도출하며, 대시보드의 범주별 주제 드릴다운(3.4)에서도 `rating`은 기본적으로 제외된다.

**판별 신호**:
- 구체적 내용 없이 평가 형용사만 사용
- 별점 기반 단순 소감
- 감탄사·욕설 단독

**예시**:
- "최고의 앱입니다"
- "별로예요"
- "그냥 쓸 만합니다"
- "쓰레기"

## 2. 다중 라벨 규칙

### 2.1 여러 유형이 섞인 경우
한 리뷰에 여러 내용이 담겨 있으면 해당되는 유형을 모두 붙인다.

**예시**:
- "앱이 자꾸 튕겨요. 그리고 내역 필터 기능 좀 추가해주세요" → `["bug_report", "feature_request"]`
- "UI가 헷갈리고 로그인도 자꾸 실패합니다" → `["user_experience", "bug_report"]`

### 2.2 라벨 개수 제한
- 최소 0개 (해당 유형 없음), 최대 3개
- 대부분은 1–2개로 분류됨

### 2.3 중첩 기준
- **버그 리포트 vs 사용자 경험**: 명시적 오류(튕김·먹통·실패)가 있으면 `bug_report`, 주관적 불편만 서술하면 `user_experience`. 오류 신호가 모호하면 버그 우선 원칙에 따라 `bug_report`를 포함한다.
  - "송금이 안 돼요" → `bug_report`
  - "송금 흐름이 불편해요" → `user_experience`
  - "송금이 자꾸 이상해요" → `bug_report` (오류 신호 모호 → 버그 우선)
- **기능 요청 vs 사용자 경험**: 요구의 성격이 **"없는 기능 추가 / 기존 기능 변경"이면 `feature_request`**, **"있는 요소의 빈도·분량·노출 줄이기"이면 `user_experience`**로 분류한다.
  - **`feature_request` (기능 추가·변경)**:
    - "다크모드 추가해주세요" → 새 기능 추가
    - "다크모드 없어서 아쉽네요" → 기능 부재 불만 (기능 갭 신호)
    - "필터 기능 추가해주세요" / "월별 필터가 필요합니다" → 새 기능 요청
    - "증권 기능 개선해주세요" → 기존 기능 개선
  - **`user_experience` (빈도·분량·정책·경험 불만)**:
    - "광고 좀 그만 띄우세요" → 광고 빈도 불만 (기능 추가·변경이 아님)
    - "팝업 그만 띄워주세요" → 팝업 분량 불만
    - "페이스페이 광고 그만 띄우세요" → 특정 기능 홍보 노출 과다에 대한 불만
    - "푸시 알림 너무 많이 와요" → 알림 빈도 불만
    - "광고 없애주세요" → 요구 형식이지만 기능 추가·변경이 아닌 노출 축소 요구
    - "메뉴가 너무 복잡해요" → 기능명 없는 일반 불편
    - "고양이미션 시간제한 생겼네요? 모아둔거 다 날아감" → 기존 기능 정책 변경에 대한 불만, 구체 요구 없음
  - **핵심 판별 질문**: "이 리뷰가 원하는 게 (1) 없던 기능을 만드는 것인가, (2) 있는 요소를 덜 보이게 하거나 옛날 정책으로 되돌리는 것인가?" (1)이면 feature_request, (2)이거나 명시적 요구 없이 불만만 있으면 UX.
  - "뭔가 좀 아쉽네요" → `user_experience` (기능명·구체 요구 없음)
- **평가 vs 사용자 경험**: 구체성 기준. "좋아요"만 있으면 `rating`, "송금이 빨라서 좋아요" 처럼 이유·상황이 붙으면 `user_experience`

## 3. 경계 사례

### 3.1 모호한 경우
- 기본적으로 **본문에 더 구체적으로 서술된 쪽**을 우선한다.
- 단, `bug_report`와 다른 유형 사이에서 애매한 경우에는 버그 우선 원칙(1장 참조)에 따라 `bug_report`를 포함한다.

### 3.2 부정적 감탄
"최악", "망했다", "다신 안 씀" 등 강한 부정 감탄만 있는 경우 → `rating` (구체 내용 없음)

### 3.3 고객센터·상담 언급
"고객센터 응답이 느려요" 같이 운영 차원의 불만은 서비스 경험이므로 → `user_experience`

### 3.4 질문만 있는 리뷰
"이거 어떻게 쓰나요?" 같은 단순 문의 → `user_experience` (앱 사용상의 혼란을 드러냄)

### 3.5 개발사 답변(reply) 처리
분류에 사용하지 않는다. 리뷰 본문(`text`)만 본다.

---

## 4. 입출력 포맷

### 4.1 입력
전처리된 리뷰 배열. 분류기에는 다음 필드만 전달한다:
```json
{
  "external_id": "...",
  "text": "..."
}
```

### 4.2 출력
각 리뷰에 `classification` 필드를 추가한다:
```json
{
  "source": "...",
  "external_id": "...",
  "author": "...",
  "score": ...,
  "text": "...",
  "posted_at": "...",
  "classification": {
    "types": ["bug_report", "feature_request"],
    "sentiment": "negative"
  }
}
```

- `types`는 `["bug_report", "feature_request", "user_experience", "rating"]` 중 해당되는 값의 배열
- 해당되는 유형이 없으면 빈 배열 `[]`
- `sentiment`는 `"positive" | "negative" | "neutral"` 중 하나 (자세한 규칙은 §6)

---

## 5. 배치 작업 규칙

- 입력 데이터: `data/*.preprocessed.json` 중 분석 기간에 해당하는 리뷰
- 출력 파일: `data/*.classified.json`
- 한 배치 크기: 20건 (너무 많으면 토큰 한도·품질 저하)
- 매 배치 시작 시 본 문서를 프롬프트에 포함
- 이미 분류된 `external_id`는 재분류하지 않음 (append 방식)

---

## 6. 감정 분류 (`sentiment`)

각 리뷰에 감정 라벨을 하나 부여한다: `positive | negative | neutral`.

**입력 범위**: 본문 텍스트(`text`)만 본다. 별점(`score`)·개발사 답변·메타데이터는 감정 판단에 쓰지 않는다.

### 6.1 중립은 최대한 지양

감정 뉘앙스가 조금이라도 드러나면 positive/negative로 기울여 판단한다. 중립은 아래 경우에만 붙인다.

- 순수 문의·질문성 리뷰 ("이체 수수료 얼마인가요?")
- 사용법·스펙 확인 같은 정보 요청 ("지문 인증 어떻게 켜나요?")
- 감정 뉘앙스가 완전히 드러나지 않는 사실 보고 ("어제부터 쓰기 시작했습니다")

조건부 칭찬·불만·미묘한 뉘앙스는 중립으로 처리하지 않는다.

### 6.2 혼재 리뷰: 부정 우선

한 리뷰에 긍정·부정 표현이 함께 있으면 **부정 신호가 하나라도 명시되면 `negative`**로 분류한다. VOC 목적이 고칠 거리 찾기라 부정을 놓치지 않는 방향으로 기운다.

**예시**:
- "송금은 빠른데 광고가 너무 많음" → `negative`
- "편한데 로그인이 자꾸 끊겨요" → `negative`
- "깔끔해요. 다크모드만 있으면 좋겠어요" → `negative` (기능 부재 아쉬움도 부정 신호로 간주)

### 6.3 판별 신호

**긍정 신호**:
- 만족·감탄·추천·감사 어휘 ("좋아요", "편해요", "빠르네요", "최고", "추천")
- 문제 언급 없이 칭찬만 있음
- 개선된 점에 대한 긍정 반응 ("업데이트 후 좋아졌네요")

**부정 신호**:
- 오류·실패·고장 언급 ("안 돼요", "튕겨요", "실패했어요")
- 불만·실망·분노 어조 ("짜증나요", "답답해요", "실망")
- "아쉽다", "불편하다", "별로다" 같은 부정 형용사
- 기능 부재에 대한 불만 어조 ("왜 X가 없어요?", "X 없어서 아쉽네요")
- "쓰레기", "최악", "망했다" 같은 강한 부정 감탄

### 6.4 유형별 기본 경향 (참고)

감정과 유형은 독립적으로 판단하지만, 실제 분포에서는 다음 경향이 강하다. 본문 해석이 모호할 때 참고만 한다.

- `bug_report`: 대부분 `negative`
- `feature_request`: 기능 부재 불만이 섞이면 `negative`, 순수 제안 어조면 본문의 나머지 톤으로 판단
- `user_experience`: 본문 감정 어휘로 판단
- `rating`: "최고"/"별로" 등 본문 어휘 그대로 따라감
